# 设计：会话、消息与提案（阶段二 M4）

上位设计：`note/superpowers/specs/2026-10-06-stage-2-database-design.md` §3.5、§3.6、§4.6、§7、§8
本 change 的 proposal：`proposal.md`
M3 的归档件（本 change 修改它的一份 spec）：`openspec/specs/document-review/spec.md`

---

## Context

三件事凑在同一批里：

1. 上位设计 §4.6 的四张 agent 表还没建，而"留学顾问"标签页是空占位（`web/components/AdvisorView.tsx`）。
2. 上位设计 §3.5 的写操作分级确认只兑现了一半：低风险动作各自有路由了（M2b 勾选材料、M3 归档材料），
   高风险的"落成提案等确认"没有表。
3. M3 明确推迟了一列：`document_reviews.run_id → agent_runs.id`（M3 归档 design 的 D10），因为
   `agent_runs` 当时不存在。

约束：

- 身份仍是匿名 cookie（`clients`），没有登录、没有角色 —— 这决定了谁能写什么（见 D4）。
- 按 `note/product/roadmap.md`，**接模型是第 3 项**，不属于 M4。所以 M4 结束时，顾问侧的消息来自维护者，
  而不是模型；这件事必须在数据里和界面上都看得出来（D2）。
- M3 立的规矩继续适用：未知就留空、不编来源、不假造日期、不删除。

## Goals / Non-Goals

**Goals:**

- 申请人能看到一条真正的对话（自己发的消息 + 顾问侧的消息），并且看得出每条顾问消息是**人**写的还是模型写的。
- 一条高风险改动可以被"提议 → 申请人确认 / 拒绝"，确认时安全地落到既有的服务上，事后可追溯。
- 一个基于旧状态的提案不会被悄悄套用。
- M3 欠的那条外键补上，并且"没有模型就不写 run"这条规则有测试钉住。

**Non-Goals:**

- 调用任何模型、prompt 工程、工具编排、流式输出、向量检索 —— 第 3 项。
- 数据标注（第 2 项）。
- 账号与角色；消息/会话/提案的删除；多轮工具调用的可视化；通知与未读计数。
- 提案的自动生成（谁在什么时机提议，是模型阶段的事；M4 只提供写入路径与确认机制）。

## Decisions

### D1 会话与消息：`seq` 在会话内连续，写入时对会话行加锁

`UNIQUE (conversation_id, seq)`，追加消息时先 `SELECT ... FOR UPDATE` 那把会话行再取 `max(seq)+1`。
这是 M3 版本号那套的同一课：让"下一条"在锁下取，两次并发写入就不会跳号，也不需要事后重算
（重算正是会跳号的地方）。不声明 ORM 关系，查询一律显式 `select()`，与 M3 的两张 document 表一致。

`role` 的 CHECK 里有 `system`（上位设计列了这个取值），M4 **不写它**：一条「系统」消息在一个还没有系统说话的阶段只会是装饰。留着这个取值是为了以后加一条真正的系统提示时不必迁移。

### D2 顾问消息的来源必须可读，而且必须显示

`messages.metadata` 里写 `origin`：M4 里只有 `"operator"`（维护者命令写入）；模型接进来之后才会有 `"agent"`。
界面**必须**把这件事显示出来，措辞要说人话（例如"由人工录入，不是模型生成"），而不是只放在 JSON 里。

理由是这个产品的红线：把一段人写的建议显示成顾问（模型）说的，和编造一条招生要求是同一类问题——读者会按
"系统算出来的"去信任它。M4 没有模型，所以 M4 的每一条顾问消息都必须是"人工录入"。

### D3 没有模型就不写 `agent_runs`

M4 建 `agent_runs`（结构按上位设计 §4.6：`message_id`、`workflow_version`、`prompt_version`、`provider`、
`model`、`latency_ms`、`input_tokens`、`output_tokens`、`tool_calls`、`confidence`），并补上
`document_reviews.run_id` 这条可空外键（还 M3 的账）。

**M4 里没有任何代码会插入 `agent_runs`。** 一行 run 的含义是"某个模型真的跑过这一次"，在没有模型的时候
写它等于伪造来源；一张空表比一行假的记录诚实。测试要钉住这一点：跑完整套流程之后 `agent_runs` 仍然是空的。

### D4 提案的**确认**走 HTTP，提案的**创建**走维护者命令

- **创建提案**由 `api/advisor_cli.py` 做。理由和 M3 的审核结论一样：产生判断的写入不开 HTTP，
  否则任何访问者都能往别人（或自己）的待确认队列里塞东西，并让界面显示"顾问建议你改档案"。
- **确认 / 拒绝**由申请人自己通过 HTTP 做。这是**申请人对自己数据的决定**，和"审核别人的材料"不是一回事：
  他确认的是"我要按这条建议改我自己的档案/组合"。把他自己的决定也塞进 CLI，等于让他打电话给维护者
  才能点一下"同意"。

### D5 确认时套用既有服务，一个事务，并记下是谁确认的

`proposals.resolved_by` 写解析者：M4 里是申请人自己（`user`）。留这一列是因为模型阶段会出现另一种解析者
（agent 提议、用户确认之外，将来还可能有"代理自动确认低风险提案"），而一个说不清"谁批准的"的审计列，
等于没有审计。

`proposals.kind` 决定用哪个服务：`update_profile` → 档案写入；`update_roadmap` / `create_task` →
`app/services/roadmap_tasks.py`；`update_application` → `app/services/applications.py`；
`archive_document` → `app/services/documents.py`。

提案只描述"要改什么"，**怎么改仍然由那些服务说了算**：它们的校验、归属规则（`origin`）、审计写入
（`task_events`）一个都不绕过。确认的整个过程在一个事务里：要么全部生效并把提案标为 `confirmed`，
要么什么都不变。确认一条已经解决的提案返回 409（不是幂等成功，也不是 500）。

### D6 基于旧状态的提案会过期，而不是被悄悄套用

提案记录的是某个时刻的状态快照，而申请人在这之后可能改了档案、路线或组合。确认前比对：**这份提案所依赖的
东西在它生成之后有没有被改过** ——

| `kind` | 依赖 | 比对 |
|---|---|---|
| `update_profile` | `profiles.updated_at` | 晚于 `proposals.created_at` 即为过期 |
| `update_roadmap` / `create_task` | `roadmap_tasks.updated_at` 的最大值 | 同上 |
| `update_application` | `applications.updated_at` 的最大值 | 同上 |
| `archive_document` | `documents.updated_at` | 同上 |

过期的确认请求返回 409，并把提案标成 `expired`；申请人可以请顾问重新提议。
不新增列：这些 `updated_at` 已经存在，而"提案之后被改过"就是"过期"的定义。

不这样做的话，最糟的情况是一个基于旧分数的选校组合建议被套到已经改过的档案上——这正是
"不要给一个编出来的基线"在提案路径上的对应物。

### D7 `risk` 表示改动的范围，不改变路径

上位设计 §3.5 把风险分成低（直接执行）与高（落提案）。M4 里**每一条提案都需要确认**，因为低风险动作
（勾选材料、归档材料）已经有它们自己的直接路由了，不需要绕道提案。

因此 `risk` 在 M4 里的作用是措辞与展示（"这会替换你整个申请组合"vs"这会新增一条任务"），而不是分支。
这一点要写在列注释与 spec 里，免得后来的人以为存在一条低风险直通的代码路径却找不到它。

### D8 `payload` 的校验交给套用它的服务

提案的 `payload` 不允许携带服务端自己写的字段（`origin`、`status`、`created_at`、id），与 M2c 的
payload 规则一致：`extra="forbid"` 的 schema 会拒绝，而不是忽略。任何校验失败都是映射过的 4xx，
不是 500——这与 `replace_applications`、`replace_roadmap_tasks` 的处理方式相同。

### D9 消息的 `metadata`：M4 只写来源；消息与提案的关联只有一个方向

模型阶段的 `tool_calls`、证据、置信度留给第 3 项。M4 的 `metadata` 只写 `origin`（D2）。
`metadata` 是 JSONB，以后加键不需要迁移。

**消息与提案之间只有一条关联：`proposals.message_id`**（上位设计 §4.6 的那一列），它回答"这条提案是在哪条
消息里提出来的"。消息侧**不**再放一个 `proposalId`：两列同时维护就有互相不一致的可能，而 M3 的 D13 已经
为同类问题定过规矩——同一件事只有一个权威来源。界面要"从消息跳到它带来的提案"时，按 `message_id` 查提案。

### D10 一个主体可以有多条会话，界面用最新的一条

不建"每个主体至多一条"的约束：那会挡住以后按主题分会话（"选校"与"签证"分开），而约束一建就要迁移。
M4 的界面读会话列表并展示最新一条；申请人的消息写进那条会话。

### D11 M4 不删除任何东西

没有删除会话 / 消息 / 提案的路由。拒绝是一条状态（`rejected`），不是删除。与 M3 的决定一致。

### D12 交付拆两个 PR，同一个 change

- **PR 1（后端）**：迁移与模型、会话与提案的服务与路由、`agent_runs` 与那条外键、`advisor_cli.py`、后端测试。
- **PR 2（前端）**：`AdvisorView` 的真实对话视图、适配层与接口调用、走查步骤与截图。

先合后端，前端才接得上；两个 PR 各自可独立验证（与 M3 的 D15 同样理由）。

## Risks / Trade-offs

| 风险 | 处理 |
|---|---|
| 没有模型时，"顾问"页面可能被理解成模型在说话 | D2：来源写进 `metadata` 并由界面明确显示；走查断言这句话出现在页面上 |
| 提案被套用到已经变了的档案上 | D6 的过期规则 + 409，并有测试 |
| 确认提案绕过既有服务的规则（例如 `origin` 归属） | D5：只调用既有服务，不自己写表；测试断言确认之后 `task_events` 里有对应记录 |
| 一张空的 `agent_runs` 看起来像"忘了写" | D3 写进 spec 与列注释，并有测试断言它保持为空 |
| 并发追加消息导致 `seq` 跳号 | D1 的行锁；测试用两个线程同时追加并断言语义连续 |
| 测试清扫：新表挂在 `clients` 上 | `conftest` 的既有主体清扫靠数据库级联，新表一律 `ON DELETE CASCADE`，不需要改清扫顺序；测试仍要跑两遍确认 |

## Migration Plan

1. 一条新迁移：建 4 张表 + `document_reviews` 加一列可空外键（用 `use_alter` 或分两步，`agent_runs` 先建）。
2. 必须能从空库一次建全，也要能 `alembic downgrade -1` 干净回退（先 drop 那条外键，再 drop 四张表）。
3. 不新增种子数据：M4 没有需要预置的配置行。**不 seed 任何示例会话**——示例数据会被当成真的对话。
4. 回滚：`alembic downgrade -1` 删表；`document_reviews.run_id` 列一并撤销。
5. 部署：M4 不改变部署方式。线上那两个已知限制（本地存储根、Vercel 请求体上限）与本批次无关。

## Open Questions

1. **申请人能不能自己发消息？** 我按"能"写（否则对话页只能读）。若希望 M4 只读、把输入框留到模型阶段，
   `messages` 的写入方就只有 CLI 一侧，任务会少一块。
2. **顾问侧消息在 M4 只由维护者命令写入**（并标明"人工录入"）。要不要加一个不回话的"回声"让页面更好演示？
   我建议不加：那会把非模型的话显示成顾问的话，正是 D2 要避免的。
3. **`risk` 在 M4 只有一个实际取值**（见 D7）。保留它（上位设计有，界面措辞会用到），还是现在就不建这一列？
4. **过期规则用"依赖的状态在提案之后被改过"来判定**（D6）。可以接受吗？另一种做法是给提案加一个有效期
   （例如 24 小时），但那会引入"过多久算旧"这个没人能拍的数字。
5. **界面对多条会话只展示最新一条**（D10）。在只有一条会话的现在够用，以后要切换会话时再加选择器。
